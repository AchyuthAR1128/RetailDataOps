## 1. Overview

The **Bronze Ingestion Engine** ingests raw landing CSV batches (`sales_slice.csv`, `calendar_slice.csv`, `sell_prices_slice.csv`) generated by the Replay Simulator into append-only Delta Lake tables located under `data/bronze/`.

Bronze tables preserve raw source data with minimal transformation while enforcing strict physical integrity, manifest checksum verification, PySpark `FAILFAST` schema checks, intra-batch deduplication, deterministic row hashing, and inter-batch idempotency.

---

## 2. Ingestion Architecture & Safeguards

```
data/landing/<batch_id>/
├── manifest.json
├── calendar_slice.csv
├── sales_slice.csv
└── sell_prices_slice.csv
       │
       ▼ [1. Pre-flight Checksum Check (Physical SHA256 vs manifest.checksums)]
       │
       ▼ [2. Header & Schema Validation (Matches meta + manifest.day_keys)]
       │
       ▼ [3. FAILFAST PySpark CSV Reader + Row-Count Reconciliation]
       │
       ▼ [4. Intra-batch Duplicate Business Key Check & Row Hash Computation]
       │
       ├───────────────────────┬───────────────────────┐
       ▼                       ▼                       ▼
data/bronze/calendar    data/bronze/sell_prices  data/bronze/sales
(Delta Table)           (Delta Table)           (Delta Table)
```

## 3. Bronze Metadata Standards

Every Bronze record includes 4 standardized metadata columns:

| Metadata Column | Type | Description |
|---|---|---|
| `batch_id` | `STRING` | Batch directory name (e.g., `batch_20110129_20110204`). |
| `source_file` | `STRING` | Original source file name (e.g., `sales_slice.csv`). |
| `ingest_ts` | `TIMESTAMP` | Execution timestamp when the record was ingested into Bronze. |
| `row_hash` | `STRING` | SHA256 hex string computed deterministically from pipe-delimited source column values (`col1\|col2\|__NULL__`). Excludes runtime metadata. |

---

## 4. Idempotency & Immutability Rules

1. **Append-Only Immutability**: Existing records in Bronze Delta tables are **never** updated or deleted.
2. **Same-Batch Replay**:
   - If a `batch_id` already exists in a Bronze table, the engine validates that the existing row count, business keys, and `row_hash` set match the incoming batch 1:1.
   - If **identical**, the write to that table is skipped cleanly as a **safe no-op**.
   - If **conflicting** (different row count, keys, or hashes), an `IdempotencyConflictError` is raised.
3. **Controlled `d_*` Schema Evolution**:
   - `bronze_sales` uses `mergeSchema=true` *only* after confirming incoming `d_*` columns match `manifest.day_keys`.
   - Historical rows from previous batches remain unchanged on disk and evaluate newly added `d_*` columns as `NULL`.

## 5. Usage Guide

### Command Line Interface (CLI)

```bash
# Ingest a specific landing batch into Bronze
python scripts/run_bronze.py --batch-id batch_20110129_20110204

# Run with custom directories
python scripts/run_bronze.py --batch-id batch_20110129_20110204 --landing-dir data/landing --bronze-dir data/bronze
```

### Python API

```python
from retaildataops.bronze import BronzeIngestor
from pyspark.sql import SparkSession

spark = SparkSession.builder.appName("RetailDataOps").getOrCreate()
ingestor = BronzeIngestor(spark=spark, landing_dir="data/landing", bronze_dir="data/bronze")
counts = ingestor.ingest_batch("batch_20110129_20110204")
print(f"Ingested {counts['sales']} sales records.")
```
